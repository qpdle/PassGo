# Общий стенд

Стенд запущен: https://passgo-51-250-38-112.sslip.io. Статический IP 51.250.38.112. Сертификат получен, интерфейс и API доступны по HTTPS.

Нужен Linux сервер с Docker и доменом. Для небольшого учебного стенда можно начать с 1 ГБ памяти и готовой сборки интерфейса; 2 ГБ дают больше запаса. На сервере с 1 ГБ сборка может потребовать дополнительную память. На этом стенде используется ВМ Яндекс Cloud с 2 ГБ памяти и SSD 20 ГБ. Расчёт стоимости — 1700,29 рубля за месяц непрерывной работы без дополнительного трафика. Используется стартовый грант.

Порядок запуска:

1. Получить файлы проекта на сервер.
2. Направить домен на IP сервера. Открыть порты 80 и 443.
3. Скопировать .env.production.example в .env.production.
4. Заполнить случайный DJANGO_SECRET_KEY и POSTGRES_PASSWORD. Вписать домен в PASSGO_DOMAIN и DJANGO_ALLOWED_HOSTS, адрес с https в DJANGO_CSRF_TRUSTED_ORIGINS.
5. Выполнить `docker compose -f compose.production.yml up --build -d`.
6. Открыть сайт и /api/v1/health/ через HTTPS. Проверить вход в админку и работу интерфейса.

Caddy получает сертификат после настройки домена и доступности портов. Интерфейс и API работают на одном домене. База и backend не имеют открытых внешних портов. Данные PostgreSQL и сертификаты сохраняются в томах. DEBUG выключен, демонстрационный маршрут в этом режиме недоступен. Для проверки интерфейса на стенде используется страница «Связь с сервером».

Создать администратора: `docker compose -f compose.production.yml exec backend python manage.py createsuperuser`.

Не использовать `down -v`, если нужно сохранить базу. Локальная .env.production не отправляется в Git.

## Обновление второго спринта

На общем адресе работают новые формы и API. Миграции применены. В production проверены создание аккаунта, сессия, CSRF, площадка, два помещения, программа, публикация и запрет чужого изменения. Все записи этой проверки были откатаны одной транзакцией.

Перед обновлением сохранены база и исходники в /home/passgo/passgo-backups/s2-before. Каталог закрыт от других пользователей. Эти файлы остаются на сервере и не отправляются в Git.

Образы первой версии сохранены с меткой s1-backup. Возврат приложения: `docker compose -f compose.production.yml -f infra/compose.rollback.yml up -d --no-build`. Эта команда использует прежние образы и сохраняет текущую базу. Миграции второго спринта добавляют таблицы и не удаляют прежние поля.

Восстанавливать старую копию базы стоит только при необходимости: новые записи в ней отсутствуют. Проверка Actions для новых изменений выполняется после отправки в GitHub. Формы на телефонах нужно проверить отдельно.
