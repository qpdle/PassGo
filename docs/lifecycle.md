# Статусы и права PassGo

Правила первого спринта.
Правила предназначены для MVP бесплатных мероприятий с однократным входом. Ниже описаны окно входа и срок отмены участия.

## Пользователи и доступ

Пользователь не имеет единственной глобальной бизнес-роли. Он может быть участником одного события, организатором другого и сотрудником входа третьего. Организатор определяется через Events.owner_id. Сотрудник назначается через EventStaff для конкретного события. is_staff в Django означает доступ в техническую админку и не даёт бизнес-права организатора.

| Действие | Гость | Участник | Организатор своего события | Сотрудник назначенного события |
| --- | --- | --- | --- | --- |
| Читать публичное описание и программу | Да | Да | Да | Да |
| Читать черновик | Нет | Нет | Да | Нет |
| Создать событие | Нет | Да | Да | Да, как обычный пользователь |
| Менять событие, программу и помещения | Нет | Нет | Да | Нет |
| Назначать сотрудников | Нет | Нет | Да | Нет |
| Регистрироваться и отменять своё участие | Нет | Да | Да, для себя | Да, для себя |
| Просматривать QR билета | Нет | Только свой | Только свой | Только свой |
| Читать список участников и статистику | Нет | Нет | Да | Нет |
| Сканировать билет или вводить код | Нет | Нет | Да | Да |
| Читать результат проверки билета | Нет | Нет | Да | Да, минимальные сведения |
| Экспортировать участников и статистику | Нет | Нет | Да | Нет |

Организатор и сотрудник получают при проверке билета только имя участника, состояние билета и результат входа. Списки email и полный журнал доступны организатору. Сервер проверяет права для каждого объекта; скрытая кнопка не заменяет проверку. Для чужих непубличных объектов возвращается 404, для недоступной операции над доступным объектом — 403.

Площадки принадлежат пользователю, который их создал. Организатор использует свои площадки и помещения. После публикации вместимость и состав помещений события фиксируются; изменение справочника не меняет опубликованный план автоматически.

## Жизненный цикл события

| Переход | Условие | Результат |
| --- | --- | --- |
| draft → published | Организатор; заполнены название, даты, период регистрации, вместимость и помещения | Открывается публичная страница |
| draft → cancelled | Организатор | Черновик больше не редактируется |
| published → cancelled | Организатор; событие ещё не завершено | Новые регистрации и входы запрещены, активные регистрации отменены, билеты отозваны |
| published → completed | Серверное время достигло ends_at | Доступны история и статистика, новые входы запрещены |

Другие переходы запрещены. Возврат в черновик, возобновление отменённого события и физическое удаление опубликованного события в MVP не предусмотрены. Завершение выполняется фоновым заданием, но API независимо проверяет ends_at и не зависит от своевременного запуска задания.

В опубликованном событии можно менять описание и программу до starts_at. Нельзя уменьшать лимит ниже числа активных регистраций. Даты, окно входа, площадки и помещения после публикации не меняются в MVP, чтобы ранее выданный билет оставался достоверным. После начала события административные изменения программы блокируются.

## Регистрация и билет

Одна запись Registrations на пару event_id и user_id хранит текущее участие. Статусы регистрации: active и cancelled. Факт посещения хранится отдельно, без статуса used у регистрации.

| Переход | Условие | Действия |
| --- | --- | --- |
| Нет регистрации → active | Событие published; открыто окно регистрации; есть место | Создать регистрацию и active билет в одной транзакции |
| active → cancelled | Владелец до starts_at; факта входа нет | Отозвать билет; освободить место |
| cancelled → active | Открыто окно регистрации; есть место; входа никогда не было | Сохранить регистрацию; выпустить новый билет; старый QR не восстанавливать |
| active → cancelled при отмене события | Организатор отменяет событие | Отозвать билет; сохранить существующий факт входа |

Повторный запрос активной регистрации возвращает существующую регистрацию и билет. После фактического входа участник не может отменить участие или зарегистрироваться повторно. Административная отмена события сохраняет историю посещения даже для отменённой регистрации.

Билет имеет статусы active и revoked. Допустим только переход active → revoked. Просроченность и повторный вход определяются по датам события и CheckIns, а не отдельным статусом билета. Отзыв билета в MVP выполняется при отмене участия или события, а не отдельной командой сотрудника.

## Время и допуск на вход

Все даты хранятся как timestamptz в UTC; Events.timezone хранит имя IANA, например Europe/Moscow. Интерфейс отображает даты в часовом поясе события. Источник решения — серверное время, а не часы телефона.

Предложенное окно входа: от starts_at минус 60 минут включительно до ends_at исключительно. Регистрация открыта при registration_opens_at ≤ now < registration_closes_at, причём registration_closes_at ≤ starts_at. Отмена участия разрешена до starts_at исключительно.

Вход разрешён, если событие published, время в окне входа, сотрудник назначен на это событие, регистрация active, билет active и CheckIns ещё не существует. Проверка токена сама по себе не создаёт вход; подтверждение сервером одновременно проверяет условия и создаёт CheckIns.

Результаты проверки: accepted, already_checked_in, invalid_ticket, revoked_ticket, wrong_event, checkin_not_open, event_cancelled, event_completed. При повторе accepted возвращается already_checked_in с временем первого входа. При ошибке сети интерфейс не показывает успешный вход; повтор запроса позволяет узнать фактический результат.

QR содержит случайный непрозрачный токен без имени, email или порядкового номера. Ручной ввод использует тот же токен. Токен не даёт права на вход без авторизации сотрудника и проверки назначения.

## Статистика

Активные регистрации — количество Registrations со статусом active. Уникальные посещения — количество CheckIns события. Доля посещения для обычного завершённого события равна посещениям / активным регистрациям × 100; при нулевом знаменателе отображается 0%. Для отменённого события доля не вычисляется, поскольку регистрации отменяются; факты посещения сохраняются. Нельзя смешивать число успешных входов и число попыток сканирования.

## Проверка правил

1. Пользователь другого события не читает черновик, билет и статистику.
2. Сотрудник события А не подтверждает вход на событие Б и не экспортирует участников.
3. Отмена регистрации отзывает старый QR; повторная регистрация выпускает новый.
4. После входа отмена участником запрещена; отмена события сохраняет CheckIns.
5. На границах времени регистрация и вход проверяются по полуоткрытым интервалам.
6. Два запроса на последнее место создают не больше одной активной регистрации.
7. Два подтверждения одного билета создают ровно один CheckIns.

Проверка этих сценариев относится к реализации в следующих задачах. Здесь описаны правила окна входа и повторной регистрации.
