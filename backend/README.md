# Backend PassGo

S1-08: минимальный Django + DRF с PostgreSQL в Docker Compose. Единственный маршрут — проверка здоровья. S1-09 добавляет accounts.User, Event, Venue, Room, сессии и техническую админку. Бизнес API пока не реализован; стандартный auth.User не используется.

## Запуск

1. Запустить Docker Desktop с Linux containers.
2. В корне репозитория скопировать `.env.example` в `.env`.
3. Задать случайный `DJANGO_SECRET_KEY` и `POSTGRES_PASSWORD`. Не публиковать `.env`.
4. Выполнить `docker compose up --build -d` из корня. Первый запуск загружает образы и зависимости. Миграции запускаются перед сервером, база должна пройти healthcheck.
5. Открыть `http://127.0.0.1:18000/api/v1/health/`. Ответ 200: `{"status":"ok"}`. Поддерживается и адрес без завершающего слеша.

Порт задаётся `BACKEND_HOST_PORT`. PostgreSQL не публикуется на порту компьютера. Сервер слушает только localhost. Dockerfile использует Python 3.12, зависимости закреплены в requirements.txt. Образы Python и PostgreSQL закреплены по основной версии, а не digest.

## Проверки и остановка

`docker compose ps` — состояние контейнеров.

`docker compose exec backend python manage.py check` — проверка Django.

`docker compose exec backend python manage.py showmigrations` — список миграций.

`docker compose logs --tail 30 backend` — сообщения запуска.

`docker compose restart` — перезапуск с сохранением данных.

`docker compose down` — удалить контейнеры и сеть, сохранив именованный том. `docker compose up -d` восстанавливает запуск. Не использовать `down -v`, если данные нужно сохранить.

При недоступной базе health возвращает 503 `{"status":"unavailable"}`, без адресов, настроек и текста исключения. Проверка выполняет SELECT 1, а не просто сообщает о работающем процессе.

Это локальная среда разработки с runserver. HTTPS, производственный сервер и DEBUG=false относятся к S1-14. Health остаётся публичным; будущие DRF представления по умолчанию требуют авторизации. Формат ошибок бизнес API подключается позднее по S1-06.

## Модели и демо данные S1-09

Собственная модель пользователя — `accounts.User`: email вместо username, full_name, стандартные пароли и технические права Django. Email приводится к trim + lowercase; уникальный индекс lower(email) запрещает дубли независимо от регистра. Не изменяйте AUTH_USER_MODEL после создания базы с пользователями.

Начальные бизнес модели: `events.Event`, `events.Venue`, `events.Room`. Ограничения PostgreSQL проверяют вместимость, порядок дат, окно регистрации, допустимые статусы и уникальность названия помещения внутри площадки. Проверку timezone и 60-минутного окна входа выполняет `Event.full_clean()`; обычный `save()` не заменяет её. Будущие сервисы обязаны вызывать валидацию и соблюдать правила S1-04.

Запуск Compose автоматически применяет миграции. Для проверки схемы: `docker compose exec backend python manage.py makemigrations --check --dry-run`. Тесты: `docker compose exec backend python manage.py test accounts events config`. Тестовый запуск создаёт отдельную временную PostgreSQL базу и удаляет её после завершения; рабочий том не очищается.

Демо набор: `docker compose exec backend python manage.py seed_demo`. Команда доступна только при DEBUG=true, повторный запуск не создаёт дубли и не перезаписывает изменённые записи. Если демонстрационный email уже занят другим профилем, команда отказывается от заполнения и откатывает транзакцию.

Создаются 3 вымышленных пользователя с адресами в домене `passgo.example`, площадка, 2 помещения и 1 черновик события. У демо пользователей нет пригодных паролей и доступа к админке. Имена «организатор», «участник» и «сотрудник» обозначают образцы профилей: назначения EventStaff, участие и билеты ещё не реализованы. Даты примера фиксированы; команда не сдвигает их вслед за текущей датой.

Админка: `http://127.0.0.1:18000/admin/`. Создать личный технический аккаунт интерактивно: `docker compose exec backend python manage.py createsuperuser`. Ввести свой email, full_name и пароль; пароль не записывать в Git. Готового пароля администратора в коде нет.

Пользователей можно создавать и редактировать через стандартные формы Django. Мероприятия, площадки и помещения зарегистрированы только для просмотра: добавление, изменение и удаление отключены до реализации общих бизнес сервисов. is_staff/is_superuser дают технический доступ в админку и не являются бизнес ролями мероприятия.

Включены сессии для админки и стандартные валидаторы пароля. Health остаётся публичным, остальные будущие DRF представления по умолчанию требуют авторизации. JSON signup/login, адаптер 401 по контракту S1-06 и бизнес API здесь не реализованы. Файлы статики админки локально обслуживаются runserver при DEBUG=true; production конфигурация относится к S1-14.
